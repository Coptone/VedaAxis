# VedaAxis 架构基线

## 1. 交付策略

项目采用“阶段交付、门槛验收”的方式完成完整 MVP。阻断 PoC 未通过时，后端与网页可以继续开发，但插件能力不得标记为可上线。

## 2. 模块边界

服务端先采用模块化单体，避免在领域和流量尚未稳定时引入分布式事务。模块边界与 PRD 一致：身份、游戏数据、遭遇、计划、规则、AI 编排、执行统计。模块间只通过服务接口和不可变 DTO 交互，未来可以按边界拆分。

插件在开怪前下载不可变计划快照，战斗中只依赖本地状态机。服务端故障不会中断已加载的一把战斗。
战斗结束时插件先把执行批次写入本地待上传队列，再异步上传；网络失败保留文件并在后续连接时重试，服务端以 `fightExecutionId` 幂等去重。

## 3. 战斗生命周期

首版以游戏的 `InCombat` 状态作为时间轴自动开始信号。只有插件已加载并校验不可变计划快照，且当前 Territory 与计划遭遇元数据匹配时才能启动；启动必须幂等，重复事件不能重置正在运行的时间轴。脱战采用短延迟去抖，团灭/重新开始和副本完成使用 Dalamud Duty 事件立即结束或清理，并且一把战斗只生成一个执行批次。

`0.1.4` 已把 Territory 加入计划契约 1.1，并由在线计划、API 与插件共同传递；`0.1.5` 的计划契约 1.2 进一步持久化阶段和机制。插件界面显示当前区域、计划区域和拒绝启动原因。首个验证遭遇为 O8S（Territory 755），用于关闭自动生命周期和在线数据 PoC，不替代 DMU 时间轴证据。手动开始/停止保留为诊断能力；用户倒计时触发延后，不能成为首版自动触发的依赖。

计划契约 1.3 为每个阶段保存 `durationMs` 与 `timingMode`。`ABSOLUTE` 阶段从计划起点按固定绝对时间运行，不因输出提前转场；`RELATIVE` 阶段保留阶段内相对间隔，但允许运行时由阶段结束事件提前切换。`0.1.7` 只加载 P1/P2 两个 `ABSOLUTE` 阶段，P3 的提前转场检测仍属后续范围。

## 4. 轨道模型

轨道是位置而不是职业：

- 四人模式：`T1/H1/D1/D2`。
- 八人模式：`MT/ST/H1/H2/D1/D2/D3/D4`。

轨道记录允许职业集合；当前队伍只有唯一兼容结果时自动绑定，多解或重复职业时要求一次人工选择并按遭遇、计划与队伍签名记忆。

单体任务可携带 `targetTrackId`。插件根据目标轨道的允许职业在当前队伍中做唯一匹配，因此不依赖本地队伍列表排序；匹配为零或多解时，用户可在非战斗状态手动选择成员。当前手动映射只保存在内存中，重载计划或退出插件即清除，避免持久化角色名。

## 5. 高亮实现

插件读取原生 ActionBar 可见槽位及其 Action ID，在 Dalamud UI 绘制周期中为所有匹配槽位绘制覆盖层。实现不触发技能、不模拟输入、不改写热键栏内容。未找到技能时显示独立诊断。

单体目标使用相同的只读原则：插件读取 `_PartyList` 的可见成员节点，在 ImGui 前景层叠加状态色，不修改原生队伍列表节点。姓名仅用于本帧定位，优先匹配可见姓名并以队伍索引兜底。

## 6. 版本与兼容

所有计划快照携带 `schemaVersion`、`timelineVersion`、`planVersion` 和 `minimumPluginVersion`。插件只接受其声明支持的 Schema；不兼容版本不能静默启用。

时间轴锚点以 `Action ID + 发生序号 + 观察类型 + 计划时间 + 偏移` 表达。插件分别从 Boss 可见读条和 ActionEffect 接收 `CAST_START`、`ACTION_EFFECT` 锚点并校正本地时钟；未知或重复锚点由规则引擎拦截。

## 7. 数据可信度

种子时间轴和计划都保存来源、区域、游戏版本、样本量与置信状态。观察到的玩家施法时间不等于证明覆盖了机制；规则引擎必须结合技能持续时间、目标机制时间和实际效果验证。

机制展示将攻击类别与伤害属性分开：`RAIDWIDE` 显示为 AOE，普通 `Attack` 显示为平 A，`TANK_BUSTER` 显示为死刑；物理、魔法、特殊和未知属性另行标注。每个直接伤害机制可选携带 `damageProfile`，必须记录数值口径、统计量、样本量、来源和置信状态；有直接伤害但没有可追溯校准时只能显示“伤害值待校准”，不能用名称猜测数值。开场、阶段切换、Boss 归位、纯咏唱和判定等不对应一次直接承伤的行显示为“时间轴标记”，不再误报缺少伤害值。

技能效果目录来自固定游戏数据版本的人工复核快照，区分全伤害/物理/魔法减伤、最大生命护盾、治疗威力护盾、无敌特判、作用范围和不可叠加组。计划编辑器以每个受击轨道为目标计算当前安排：百分比减伤乘算，不可叠加组只计最强项，且只有允许施放窗口能够覆盖机制命中时才纳入结果；AOE 显示全队轨道中的最高减伤后伤害，死刑显示坦克轨道中的最高值。治疗威力护盾、即时治疗和无敌不从这个伤害数字中扣除，在缺少治疗属性、暴击、命中段数或机制例外证据时只列为未计入或特判提示。

减伤后伤害按连续风险带着色：AOE 为 `≤100,000` 绿色、`100,001–190,000` 黄色、`>190,000` 红色；死刑为 `≤200,000` 绿色、`200,001–289,999` 黄色、`≥290,000` 红色。颜色表达计划风险，不是存活保证，也不取代实战复盘。

FFLogs 的 `amount` 已包含该次实战的减伤、护盾和目标环境；`unmitigatedAmount` 是日志提供的原始观测量，两者都不能直接作为跨装备、跨职业和跨队伍的官方固定入伤公式。采集器可以自动列出近期公开报告并抽取不同击杀；校准器按 Action、相对时间和目标模式匹配，连续多段按单个目标求和，互斥目标分支只汇总样本，普通平 A 按逐次命中和计划 `xN` 形成整段候选，再跨报告取 P95。系统只提交不含报告码、玩家名的匿名 `POC_PENDING` 聚合产物。匹配不足的直接伤害机制保持待校准，只有完成 Action ID、伤害属性、目标模式、版本和实战复核后才能提升置信度。观察样本不会产生“100% 必定存活”的通用保证。

外部时间轴采用“按用户提供 URL 即时获取候选”而非定时镜像。服务端只允许固定 HTTPS 来源与已知数据路径，限制响应大小、超时且拒绝重定向。Boss 阶段/机制保留来源并标为 `POC_PENDING`；玩家样本只在内存中聚合为阶段相对的匿名分位窗口，不返回或保存报告、角色及来源标识。网页必须先展示数量、警告和替换影响，由用户明确应用；应用后仍需另行保存或发布。

## 8. 在线环境

在线能力按“本地闭环 → HTTPS 测试环境 → 生产环境”推进。测试环境的最小拓扑是静态 Web、Spring Boot API 和 PostgreSQL，由反向代理统一提供 HTTPS 与 `/api` 路由；密钥只通过环境变量或服务器密钥设施注入，数据库使用持久化卷、迁移、备份和可回滚发布。当前 API 没有 Redis 依赖，因此 Redis 不作为首版部署前提。

插件的账户绑定、计划同步和执行批次上传允许访问网络，但网络调用不得进入战斗更新或绘制热路径。开怪前使用已保存的不可变快照，战斗结束先落本地队列再异步上传，测试环境必须覆盖断网、令牌刷新、重试和幂等场景。

插件设备授权采用一次性设备码，而不是在游戏插件内收集账户密码。授权成功后，Dalamud 配置保存设备 ID、短期访问令牌和可撤销的轮换刷新令牌；插件在非战斗启动阶段主动刷新并保存新令牌，访问令牌过期时也自动刷新。刷新失败但不是明确的 401 时保留本地会话与不可变计划，避免短暂断网导致重新绑定；只有服务端确认令牌无效或用户从网页撤销设备时才清除本机会话。网页只展示设备名称、时间和设备 ID 摘要，不返回令牌。

O8S 在线联调模板使用 Territory 755、策略 `O8S-POC` 和八轨模式，与 DMU Territory 1363、`DMU-P1P2` 明确隔离。该模板仅含两个贤者 ActionEffect 探针，用来验证云端计划发布、插件匹配、`InCombat` 自动开始和执行上传；它不是 O8S 攻略时间轴，也不得提升为 `VERIFIED`。

## 9. AI 边界

DeepSeek 只返回 JSON Candidate。服务端先保护锁定项和轨道边界，再执行本地规则校验；网页必须由用户明确应用候选，之后仍需另行保存或发布。API 密钥仅存在于服务端环境变量，并可通过服务器侧用户 ID allowlist 限制为指定账号可用。

AI 优化分为两种写入范围：全局优化可调整全部未锁定任务；指向优化只允许新增、删除或修改选定执行轨道上的未锁定任务，其它轨道只作为只读上下文并必须原样返回。服务端会拒绝计划外轨道、机制和技能，拒绝指向模式下的非目标轨道变更，并把 AOE、平 A、死刑和普通机制作为结构化风险字段传给模型，避免仅按裸伤害排序。对于已判定为绿色风险的机制，服务端还会拒绝 AI 新增或改动纯治疗、增疗资源和未建模护盾类任务，避免“每个机制都刷盾奶”的无效候选。
