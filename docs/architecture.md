# VedaAxis 架构基线

## 1. 交付策略

项目采用“阶段交付、门槛验收”的方式完成完整 MVP。阻断 PoC 未通过时，后端与网页可以继续开发，但插件能力不得标记为可上线。

## 2. 模块边界

服务端先采用模块化单体，避免在领域和流量尚未稳定时引入分布式事务。模块边界与 PRD 一致：身份、游戏数据、遭遇、计划、规则、AI 编排、执行统计。模块间只通过服务接口和不可变 DTO 交互，未来可以按边界拆分。

插件在开怪前下载不可变计划快照，战斗中只依赖本地状态机。服务端故障不会中断已加载的一把战斗。
战斗结束时插件先把执行批次写入本地待上传队列，再异步上传；网络失败保留文件并在后续连接时重试，服务端以 `fightExecutionId` 幂等去重。

## 3. 战斗生命周期

首版以游戏的 `InCombat` 状态作为时间轴自动开始信号。只有插件已加载并校验不可变计划快照，且当前 Territory 与计划遭遇元数据匹配时才能启动；启动必须幂等，重复事件不能重置正在运行的时间轴。脱战采用短延迟去抖，团灭/重新开始和副本完成使用 Dalamud Duty 事件立即结束或清理，并且一把战斗只生成一个执行批次。

`0.1.4` 已把 Territory 加入计划契约 1.1，并由在线计划、API 与插件共同传递；插件界面显示当前区域、计划区域和拒绝启动原因。首个验证遭遇为 O8S（Territory 755），用于关闭自动生命周期和在线数据 PoC，不替代 DMU 时间轴证据。手动开始/停止保留为诊断能力；用户倒计时触发延后，不能成为首版自动触发的依赖。

## 4. 轨道模型

轨道是位置而不是职业：

- 四人模式：`T1/H1/D1/D2`。
- 八人模式：`MT/ST/H1/H2/D1/D2/D3/D4`。

轨道记录允许职业集合；当前队伍只有唯一兼容结果时自动绑定，多解或重复职业时要求一次人工选择并按遭遇、计划与队伍签名记忆。

## 5. 高亮实现

插件读取原生 ActionBar 可见槽位及其 Action ID，在 Dalamud UI 绘制周期中为所有匹配槽位绘制覆盖层。实现不触发技能、不模拟输入、不改写热键栏内容。未找到技能时显示独立诊断。

## 6. 版本与兼容

所有计划快照携带 `schemaVersion`、`timelineVersion`、`planVersion` 和 `minimumPluginVersion`。插件只接受其声明支持的 Schema；不兼容版本不能静默启用。

时间轴锚点以 `Action ID + 发生序号 + 观察类型 + 计划时间 + 偏移` 表达。插件分别从 Boss 可见读条和 ActionEffect 接收 `CAST_START`、`ACTION_EFFECT` 锚点并校正本地时钟；未知或重复锚点由规则引擎拦截。

## 7. 数据可信度

种子时间轴和计划都保存来源、区域、游戏版本、样本量与置信状态。观察到的玩家施法时间不等于证明覆盖了机制；规则引擎必须结合技能持续时间、目标机制时间和实际效果验证。

## 8. 在线环境

在线能力按“本地闭环 → HTTPS 测试环境 → 生产环境”推进。测试环境的最小拓扑是静态 Web、Spring Boot API 和 PostgreSQL，由反向代理统一提供 HTTPS 与 `/api` 路由；密钥只通过环境变量或服务器密钥设施注入，数据库使用持久化卷、迁移、备份和可回滚发布。当前 API 没有 Redis 依赖，因此 Redis 不作为首版部署前提。

插件的账户绑定、计划同步和执行批次上传允许访问网络，但网络调用不得进入战斗更新或绘制热路径。开怪前使用已保存的不可变快照，战斗结束先落本地队列再异步上传，测试环境必须覆盖断网、令牌刷新、重试和幂等场景。

## 9. AI 边界

DeepSeek 只返回 JSON Candidate。服务端先保护锁定项和轨道边界，再执行本地规则校验；网页必须由用户明确应用候选，之后仍需另行保存或发布。API 密钥仅存在于服务端环境变量。
